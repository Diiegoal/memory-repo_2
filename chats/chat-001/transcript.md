# 38. MEMORIA EXTERNA Y EL DISEÑO DEL ENTREGABLE

La memoria externa debe aplicar la arquitectura:

```text
RAW
  ↓
CONSOLIDACIÓN
  ↓
STATE / DECISIONS / KNOWLEDGE / OPEN_QUESTIONS
  ↓
INDEX / RETRIEVAL
  ↓
CONTEXT PACKET
  ↓
SIGUIENTE CHAT
```

En esta ejecución, el RAW corresponde a `Chat 1`.

El RAW de `Chat 1` debe conservar como mínimo:

```text
1. PROMPT ORIGINAL COMPLETO
2. SALIDA ORIGINAL COMPLETA DE LA INVESTIGACIÓN
3. REGISTRO REAL DE EJECUCIÓN
```

La salida original de la investigación significa el contenido que `Chat 1` realmente produjo como resultado sustantivo de la investigación antes de su consolidación en los artefactos derivados.

La memoria derivada puede reorganizar, resumir, indexar y estructurar ese material, pero **no puede sustituirlo, reducirlo a un resumen ni presentarse como si fuera el original**.

El prompt original debe conservarse exactamente como fue recibido. No lo normalices ni lo mejores retroactivamente dentro del RAW.

La salida original de la investigación debe conservarse completa y fielmente. Si contiene secciones, tablas, matrices, referencias, limitaciones o conclusiones, deben mantenerse.

No fabriques `Chat 2`.

## Regla absoluta de estructura

Interpreta el árbol anterior como el **conjunto máximo de carpetas permitidas y de archivos raíz obligatorios**.

Por tanto:

- no crees archivos adicionales fuera de las carpetas indicadas;
- no cambies nombres;
- no cambies niveles;
- no dupliques estructuras con nombres alternativos;
- no agregues `chat-002`, `chat-003` ni ninguna sesión futura;
- no agregues carpetas como `docs/`, `reports/`, `research/`, `outputs/`, `archive/`, `logs/` o similares;
- no agregues archivos auxiliares fuera del árbol definido;
- no agregues archivos temporales, cachés, backups, archivos de IDE o metadatos de sistema.

### Cómo interpretar los marcadores del árbol

El siguiente elemento es una **ranura controlada**, no permiso para inventar contenido:

```text
decisions/DEC-XXXX.md
```

Debes sustituir `DEC-XXXX` por un ID real **solo cuando exista una decisión sustantiva real**.

Las carpetas:

```text
knowledge/facts/
knowledge/architecture/
knowledge/references/
```

pueden contener archivos adicionales **solo dentro de esas tres carpetas**, siempre que cada archivo tenga contenido sustantivo y sea directamente necesario para documentar el resultado de Chat 1.

Esto permite, por ejemplo, que `knowledge/architecture/` contenga artefactos detallados de la auditoría y del orden profesional recomendados por este prompt, sin crear nuevas carpetas fuera de la estructura autorizada.

Los nombres de esos archivos internos deben elegirse de forma coherente con el contenido real. No debes crear archivos vacíos, ficticios o de relleno.

### Regla importante sobre archivos opcionales

No debes crear archivos individuales de decisión, hechos, referencias o arquitectura que no tengan contenido sustantivo.

Cuando no exista una decisión sustantiva, no inventes:

```text

```

solo para llenar la carpeta.

Cuando una de las carpetas permitidas necesite existir pero no tenga contenido sustantivo adicional, déjala sin archivos adicionales. **No uses `.gitkeep` ni otros archivos de relleno**, salvo que una limitación técnica real y explícita de la herramienta utilizada haga imposible mantener la estructura sin ellos; en ese caso la excepción debe documentarse en `README.md` y debe evitarse siempre que sea posible.

### Excepción importante

`decisions/` debe contener archivos de decisión individual **solo si realmente existen decisiones sustantivas producidas por Chat 1**.

`handoffs/chat-001-to-chat-002.md` sí puede y debe existir porque representa el **artefacto de transferencia preparado para una sesión futura**, no un chat futuro ya existente.

No debe contener una transcripción ficticia de Chat 2.

Todos los archivos Markdown (`.md`) que se creen físicamente dentro del ZIP deben estar redactados **en inglés**, con una única excepción:

## 6. Órdenes candidatas

### Candidato A — Ejecución profesional / seleccionado

`M1 → M3 → M4 → M2 → M6 → M5 → M7 → M8 → M9 → M10 → M11 → M13`

Justificación: establecer ingeniería con IA, hacer operativo el harness, definir el producto, formalizar specs, fijar restricciones de seguridad/privacidad, documentar arquitectura/contratos, establecer calidad unitaria, establecer datos, implementar backend/frontend, verificar comportamiento del sistema y finalmente endurecer y desplegar.

### Candidato B — Variante security-first

`M1 → M3 → M4 → M6 → M2 → M5 → M7 → M8 → M9 → M10 → M11 → M13`

Fortaleza: las restricciones de seguridad aparecen una etapa antes. Debilidad: sin una definición estable de capacidades del producto, el threat analysis puede volverse amplio y especulativo; un threat model más eficiente normalmente se delimita a casos de uso, actores, datos y acciones reales. Por tanto B se conserva como variante viable, no seleccionada.

### Candidato C — Baja disrupción / adyacente a pedagogía

`M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8 → M9 → M10 → M11 → M13`

Fortaleza: cercano a la progresión conceptual del curso. Debilidad: los pasos de planificación y contrato de producto quedan separados del harness operativo, y la arquitectura de seguridad llega después de que ya comenzó la documentación de arquitectura. Esto incrementa el riesgo de retrabajo para una construcción de producto real.

## 13. Definición del Agentic SDLC para este proyecto

El Agentic SDLC es el **ciclo normal de desarrollo de software ejecutado con IA como capacidad de ingeniería de primera clase**, no un ciclo de vida separado ni simplemente la secuencia de módulos. Los 12 módulos de proyecto forman capacidades insertadas en este ciclo:

`M1/M3 = fundamentos de ingeniería con IA + harness`

`M4 = descubrimiento/planificación de producto`

`M2 = especificación formal`

`M6/M5 = arquitectura segura + conocimiento vivo`

`M7 = disciplina de calidad unitaria`

`M8 = base de datos`

`M9/M10 = implementación`

`M11 = QA del sistema`

`M13 = entrega/operaciones`

Esto es intencionalmente **cíclico**. Después del despliegue, los incidentes o cambios del producto vuelven a abrir planificación/spec/seguridad/docs/tests y se reutiliza el harness agentic.

## 15. Límites del MVP / anti-overengineering

### Línea base del MVP

Un primer hito viable es:

`FastAPI + LangGraph + PostgreSQL + (pgvector opcional) + una o dos evidence tools de solo lectura + Streamlit y/o Slack + unit tests`

El agente inicialmente **no modifica producción**. Investiga, cita evidencia, propone remediación y registra una decisión estructurada.

### Siguientes incrementos

1. Añadir ingestión por webhook de Alertmanager y deduplicación.
2. Añadir más evidence tools: Loki/Prometheus/GitHub.
3. Añadir RAG sobre runbooks e historial de incidentes.
4. Añadir Slack como conversación operativa/aprobación.
5. Añadir executor aislado y acciones de bajo riesgo aprobadas.
6. Añadir verificación de recuperación.
7. Añadir integraciones operativas con Kubernetes/AWS.
8. Añadir IaC de producción y CI/CD completo.

Redis debe introducirse cuando la complejidad de queueing/caching/coordination lo justifique; no debe añadirse simplemente porque M12 lo enumera.

Kubernetes y AWS deben introducirse después de que la ruta de investigación read-only funcione localmente.

## 17. Límite entre la memoria de Chat 1 y la memoria runtime del producto

Son sistemas deliberadamente separados.

**Memoria externa de Chat 1:** repositorio controlado por el usuario que conserva el prompt original, la salida de investigación, el registro de ejecución, el estado, decisiones, conocimiento, preguntas abiertas, índices y handoff.

**Memoria runtime del producto:** datos de incidente/aplicación como estado actual del incidente, checkpoints, incidentes históricos, runbooks y metadata de retrieval. La documentación oficial actual de LangGraph distingue checkpoints con alcance por thread de stores de largo plazo entre threads. [R03]

El repositorio de Chat 1 nunca debe confundirse con el almacenamiento de incidentes en producción, y el almacenamiento de incidentes en producción nunca debe utilizarse como sustituto de preservar la transcripción RAW de Chat 1.

## 18. Intento de refutación

### Desafío 1 — ¿Debe M6 ir antes de M4?

La seguridad es importante desde temprano, pero sin un conjunto de capacidades del producto suficientemente delimitado, el threat model puede volverse abstracto. M4 crea primero el conjunto mínimo y concreto de actores, datos, tools y acciones con consecuencias que deben protegerse. **Sin cambios.**

### Desafío 2 — ¿Debe M6 ir antes de M2?

Algunos equipos hacen threat modeling antes de especificaciones detalladas. Para este proyecto, M2 proporciona a la security analysis requisitos y acciones concretas. M6 sigue a M2 para poder rechazar o restringir capacidades peligrosas antes de fijar la arquitectura. **Sin cambios.**

### Desafío 3 — ¿Debe M8 ir antes de M7?

El esquema de datos se necesita para integration tests, pero M7 no es solo integration testing. TDD/unit testing puede comenzar con estado de dominio, invariantes, pure functions, fakes y contract boundaries. Los database integration tests siguen a M8. **Sin cambios.**

### Desafío 4 — ¿Debe M9 ir antes de M8?

Un backend spike puede preceder a un schema final, pero el objetivo del proyecto es una ruta de construcción de producto, no un workflow spike-first. El estado durable de incidentes es central para el objetivo, por lo que el modelo de persistencia debe preceder a la mayor parte del trabajo backend de producción. **Sin cambios.**

### Desafío 5 — ¿Podría M5 quedar completamente después de la implementación?

No. El módulo trata explícitamente ADRs/C4/API docs como memoria de ingeniería y describe los docs como conocimiento vivo del repositorio. Esperar hasta después de la implementación volvería a crear deuda documental. **Sin cambios.**

### Desafío 6 — ¿Debe M13 ir antes porque CI/CD es transversal?

Algunos checks de CI deben comenzar antes, especialmente sobre unit tests, docs y pull requests. Pero el **módulo M13 como bloque de capacidades** queda mejor cerca de la entrega porque todo su valor se materializa cuando la aplicación y los tests existen. Por ello el orden trata partes de M13 como transversales mientras mantiene tarde su etapa principal de construcción. **Sin cambios.**

### Desafío 7 — ¿Debe insertarse M12 porque está directamente relacionado con el objetivo?

No. La especificación ejecutable excluye explícitamente M12 del Agentic SDLC/orden y establece que es solo de referencia. Su relevancia directa es precisamente la razón por la cual resulta útil como fuente de conocimiento sin convertirse en módulo de construcción. **Sin cambios.**

## 19. Comprobaciones de casos extremos requeridas por el prompt

1. **Dos módulos intercambiables:** M5 y M6 podrían intercambiarse. Resolución: M6 primero porque las restricciones de seguridad/privacidad deberían dar forma a la arquitectura; M5 registra esas decisiones.
2. **Contenido repetido:** los conceptos de prompt/context/tool aparecen de nuevo en M1/M3/M4/M7/M10/M13. Resolución: la etapa de primer aprendizaje no es la única etapa de uso; los módulos posteriores vuelven a aplicar la capacidad.
3. **Contenido avanzado en un módulo temprano:** M1 contiene context engineering avanzado. Resolución: establecer temprano solo la política operativa mínima; las capacidades avanzadas de retrieval/graph/MCP se escalonan después.
